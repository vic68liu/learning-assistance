# ADR-0001: ADR 记录格式与决策责任

- Status: **Accepted**
- Date: 2026-11-01
- Deciders: 项目负责人（人工）
- Related: R28

## 背景

`AGENTS.md` R28 要求每个重要设计决策写 ADR，但没有定义格式与责任边界。
编码代理会生成大量"看起来像决策"的文字，若无格式约束，ADR 会退化成流水账。

## 决策

### 文件规则

- 位置：`docs/decisions/ADR-NNNN-短横线标题.md`，编号单调递增，**永不复用、永不重排**
- 一个决策一个文件；推翻旧决策时新增 ADR 并在两个文件里互相标注，
  **不得修改旧 ADR 的结论**（决策历史本身是审计证据，与 R22 同理）

### 必填结构

```
# ADR-NNNN: <标题>
- Status: Proposed | Accepted | Rejected | Superseded by ADR-NNNN
- Date: YYYY-MM-DD
- Deciders: <人名/角色>
- Related: <R## / 其它 ADR>

## 背景      —— 什么约束迫使做这个决定
## 决策      —— 一句话可执行结论，加必要细则
## 备选方案  —— 逐个列出并写明为何否决（不得只留胜出方案）
## 后果      —— 正面与负面都要写，含新增的债务
## 验证      —— 用什么测试/数据证明这个决策落地了（Layer 1/2/3）
```

### 责任边界（关键）

| 角色 | 权限 |
|---|---|
| OpenCode / 编码代理 | 可**起草** ADR，状态只能写 `Proposed`；可补齐背景与备选方案对比 |
| 人工（项目负责人） | 唯一可以把状态改为 `Accepted` 的角色 |
| 任何角色 | 不得把 `Proposed` 悄悄改成 `Accepted` |

例外：纯技术性、可逆、影响范围限于单个脚本的选择（如函数命名、日志格式）
不需要 ADR，直接写在代码注释或 PR 描述里。

### 判定"需要 ADR"的标准

满足任一即需要：

1. 引入或移除外部依赖
2. 改变数据契约/Schema 的语义（非新增可选字段）
3. 影响教育伦理判定口径（掌握度、独立性、证据使用）
4. 影响验证可信度（什么算 `program_verified`）
5. 影响学生数据的采集、留存、脱敏
6. 放弃某个方案且未来可能有人重新提出

## 备选方案

- **用 Issue/PR 描述代替 ADR** —— 否决：PR 会沉没，无法在编码时强制回查；
  且本项目大量决策由编码代理做出，需要可 diff 的静态记录。
- **单一 DECISIONS.md 追加式文档** —— 否决：无法独立引用编号，
  多人/多代理并发编辑易冲突，历史结论有被就地篡改的风险。

## 后果

- 正面：每个决策有编号可被代码/文档引用（如 `ADR-0002` 被 `math_check.py` 引用）；
  状态字段让"待定"与"已定"在文件名之外可机器区分。
- 负面：多 7 个文档要维护；起草 ADR 会增加编码代理的输出量。
- 债务：本 ADR 自身在被推翻时也需要新编号文件，编号会持续增长，可接受。

## 验证

Layer 1：`scripts/validate_docs.py`（P8 前实现）检查每个 ADR 文件含六个必填小节、
Status 取值合法、`Accepted` 的 ADR 必须有非空 `Deciders`。
当前该脚本未实现，**此项验证处于未执行状态**，靠人工核对。
