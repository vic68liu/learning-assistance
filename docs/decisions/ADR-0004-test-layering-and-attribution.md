# ADR-0004: 测试分层与归因

- Status: **Proposed**（待人工批准）
- Date: 2026-11-01
- Deciders: OpenCode 起草
- Related: R7、R25、R26、ADR-0002、ADR-0007

## 背景

原方案在 `skills/*/tests/` 放"≥20 个测试用例"，又在 `benchmark/` 放"≥30 个案例"，
两者都用 `cases.json` 命名，语义混在一起。后果是：

- 断言不了的东西被写成"测试"，于是"测试通过"变成一句无法核查的话（违反 R25）
- 模型输出质量下降时，无法判断是**模型能力**问题还是**Prompt / 知识库 / 数据 / 验算**问题

## 决策

三层，每层的**对象、工具、判定方式、能否自动断言**都不同。

### Layer 1 — 单元测试（确定性代码的行为）

| | |
|---|---|
| 位置 | `tests/` |
| 对象 | `scripts/*.py` 的纯函数与文件操作 |
| 工具 | pytest |
| 判定 | 断言全部通过 |
| 硬约束 | 不调用模型、不读学生数据、可离线重复 |

`AGENTS.md` 第 10 节列的四条必跑命令里，`pytest` 就是这一层。

### Layer 2 — 契约测试（模型输出的结构合规）

| | |
|---|---|
| 位置 | `scripts/validate_*.py`，输入为模型真实输出文件 |
| 对象 | ① Schema 合规 ② 枚举取值合法 ③ 知识点 ID 存在于知识库 ④ `evidence_id` 真实存在 ⑤ confidence 有 basis 或为 null |
| 工具 | jsonschema + 自定义规则 |
| 判定 | **合规率必须 100%**；任何一条不合规即该阶段验收失败 |
| 硬约束 | 不评判内容好坏，只看结构；不判定数学对错（那是 ADR-0002 的事） |

这一层能自动断言，因此"homework-analysis 输出 Schema 合规率 100%"是一句可核查的话。

### Layer 3 — Benchmark（语义质量评分）

| | |
|---|---|
| 位置 | `benchmark/` |
| 对象 | 模型输出的内容质量：诊断是否合理、提示是否泄露答案、题目是否适合独立验证 |
| 工具 | 人工评分为主 + 评审模型辅助；`gold_output` 来自 `test-data/` 人工审核版本 |
| 判定 | 0~5 分维度打分，**必须展示具体失败案例** |
| 硬约束 | `model_output` 必须来自真实模型调用并记录 `model_id`、`prompt_version`、原始响应 |

评分规则（沿用原方案）：

```
0 完全失败 | 1 严重错误 | 2 部分正确 | 3 基本符合要求 | 4 质量良好 | 5 完全符合要求
```

### 归因要求（本 ADR 的核心）

每个失败案例必须落进且只落进一个 `failure_category`：

| 类别 | 判定证据 |
|---|---|
| `model_capability` | 同一 Prompt 下另一模型也失败，且结构合规（Layer 2 通过） |
| `skill_prompt` | 修改 SKILL.md 措辞后同模型通过 |
| `knowledge_base` | 失败源于知识点缺失/粒度不当/关系错误（Layer 2 报 unmapped 或 ID 不合法） |
| `test_data` | gold 标准本身有错或题干歧义（人工复核后修正） |
| `math_verification` | 结论正确但验算降级/失败，或验算器 bug |

归因规则要写进 `scripts/compare_models.py`，报告里必须有五类占比。
**没有归因的分数没有决策价值。**

### 回归基线

```
run_benchmark.py --model qwen --prompt-version v3
compare_models.py --current <run_id> --baseline <run_id>
```

改 Prompt 后必须与历史基线对比；报告需列出**分数下降的具体 case_id**，
不得只报平均分变化。这是防止"整体没变差、但把已修好的题又弄坏了"的唯一手段。

## 备选方案

1. **只有一套 `cases.json`（原方案倾向）** —— 否决：无法区分"结构不合法"与"内容不好"，
   且会让结构违规在评分中靠"部分正确"蒙混过关。
2. **全自动 LLM-as-judge 打分** —— 否决：评审模型自身的偏差会污染基准，
   而 PoC 阶段正是要判断模型能力；初期必须人工评分建立基准，
   之后才可用评审模型做扩量，并保留 10% 人工抽检校准。
3. **用单元测试断言模型输出** —— 否决：模型输出不确定，
   断言它等价于把 Prompt 的每次措辞变化都变成"测试失败"。

## 后果

- 正面：三类问题（结构 / 内容 / 代码）互不污染；分数变化能追溯到原因；
  "测试通过"这句话重新变得可核查。
- 负面：需要维护三套产物；人工评分成本高（P9 的 ≥30 案例即由此而来）；
  归因判定本身需要纪律，否则容易被随手填写。
- 债务：`failure_category` 的判定规则初期靠人工，需要在积累 ≥50 个失败案例后固化为脚本规则。

## 验证

- Layer 1 自身：`tests/test_validate_schemas.py` 覆盖"故意破坏 Schema → 必须非零退出"
- Layer 2：P4 验收需给出实测合规率与不合规样本清单
- Layer 3：P9 报告必须含五类归因占比 + 具体失败案例 + 与基线的 case 级 diff；
  缺任一项即视为报告不合格

**当前状态**：`scripts/` 与 `tests/` 在 commit 3 落地 Layer 1/2；
`benchmark/` 与 `compare_models.py` 属 P9，尚未实现。
