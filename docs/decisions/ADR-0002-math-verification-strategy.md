# ADR-0002: 数学验证依赖选型 —— sympy + 数值双验

- Status: **Accepted**
- Date: 2026-11-01
- Deciders: 项目负责人（人工批准引入 sympy）
- Related: R21、R7、ADR-0007

## 背景

原始方案有两条要求互相冲突：

1. "数学答案必须进行独立验证"，且 `verification_status` 存在 `program_verified` 档位
2. "使用标准库或经过明确批准的依赖"，且"不允许 `eval()`"

七年级数学的验证需求包含四类：有理数四则与乘方、去括号与合并同类项、
一元一次方程求解、代数式求值。后三类是**符号运算**，标准库无法完成
（`fractions`/`decimal` 只能算数值，不能判断 `-(2x-3)+x` 与 `-x+3` 是否恒等）。
若只用标准库，`program_verified` 对最核心的代数内容永远拿不到。

## 决策

引入 **sympy**，采用**符号验证 + 数值抽样双验**，两者一致才允许 `program_verified`。

### 强制管线（`scripts/math_check.py`）

```
模型/输入给出的表达式字符串
  → ① 白名单解析器（受限文法，自建 AST）        失败 → needs_human_check
  → ② 由 AST 构造 sympy 表达式（不用 sympify 直接吃原文）
  → ③ 符号判定：simplify(a - b) == 0 / solveset 解集比较
  → ④ 数值双验：对自由变量随机抽样（含 0、±1、±大数、分数点）代入求值，
                用 Fraction/mpmath 比较，容差 0（精确）或 1e-9（浮点残余）
  → ⑤ ③④一致 → program_verified
     ③④不一致 → needs_human_check，并记录 reason=symbolic_numeric_disagreement
     ③ 或 ④ 异常/超时 → needs_human_check，记录降级原因
```

**关键点**：sympy 只接受由我们自己 AST 构造出的表达式，**不接受模型原始字符串**。
`sympy.sympify` 底层走 Python 求值，直接喂模型输出等于变相 `eval()`，违反 R21。

### 白名单文法

允许：数字（整数/小数）、变量 `x` `y`、运算符 `+ - * / ^`、一元负号、括号、
分数写法 `\d+/\d+`、根号 `sqrt(...)`、等号（用于方程）。
拒绝：任何字母序列（除单字符 `x`/`y`）、函数名、下划线、逗号、分号、
`import`/`lambda`/`__` 等片段、单字符外的标识符、非 ASCII 数学符号（先归一化再解析）。
归一化只允许确定性的字符映射（如 `×`→`*`、`÷`→`/`、`−`→`-`、`（）`→`()`），
**语义猜测一律禁止**（R11），例如不猜 `2 1/3` 是带分数还是乘法。

### 预期 verification_status 分布（目标，非承诺）

| 题型 | program_verified 目标 |
|---|---|
| 有理数四则 / 乘方（第1、2章） | ≥ 95% |
| 去括号 / 合并同类项（第4章） | ≥ 85% |
| 一元一次方程求解（5.2） | ≥ 80% |
| 实际问题与几何题（5.3、第6章） | **不设目标，预期以 needs_human_check 为主** |

最后一行是刻意的：这类题的语义无法符号化，**伪装成已验证比承认未验证危险得多**（R25）。
这也是第 6 章暂缓进入 PoC 的核心理由（ADR-0006）。

### 依赖与离线要求

- sympy 版本写入 `requirements.txt` 并锁定主次版本
- benchmark 运行期间不得依赖网络下载 sympy（离线可复现是回归对比的前提）
- sympy 异常**不得**穿透到 Skill 输出层，必须在 `math_check.py` 内捕获并转成降级结论

### 无法验证时的口径

`needs_human_check` 不是失败，而是一个必须诚实携带的结论。
Skill 不得为了让输出"看起来完整"而擅自把 `needs_human_check` 升级为 `model_checked`。

## 备选方案

1. **仅标准库白名单解析** —— 否决。代数恒等判断无解，`program_verified` 名存实亡，
   全部代数题落在 `model_checked`（模型自己算、模型自己判），
   等于放弃"独立验证"，违背方案最核心的可信度主张。
2. **调用外部 CAS/WolframAlpha API** —— 否决。引入网络依赖与数据外发（学生题目出域），
   与 R23 冲突，且不可离线复现。
3. **纯数值验证（把表达式当黑盒随机取值比较）** —— 否决为主方案，采纳为辅助。
   数值法能发现不等，但不能证明恒等（假阳性风险：随机点恰好避开差异）；
   且方程类无"值"可直接比。故必须与符号法**双验**，单独使用不可。
4. **LLM-as-judge 判数学对错** —— 否决。用模型验证模型不是独立验证，
   只可用于 `model_checked` 这一较低档位。

## 后果

- 正面：代数结论有真正的独立验证路径；降级口径明确，可统计可信度分布。
- 负面：新增第三方依赖（sympy 体积较大、导入慢）；
  白名单解析器本身是需要持续测试的自研代码，**它的 bug 会导致错误答案被判正确**
  —— 这是本决策最大的残余风险。
- 债务：白名单文法初期较窄（不支持绝对值、不等式、多字母多项式），
  扩展时必须同步增加 Layer 1 用例（R26）；应用题仍无解，靠后续 OCR spike 与人工抽检。

## 验证

- Layer 1：`tests/test_math_check.py` —— 含四类必测：
  ① 去括号漏变号（`-(2x-3)+x` vs `-x+3` 必须判不等）
  ② 负数乘方括号（`-2^4` vs `(-2)^4` 必须判不等；`(-2)^4` vs `16` 必须判等）
  ③ 非法字符注入（`__import__("os")`、`x = 1`、`lambda: 1` 必须被拒绝）
  ④ 双验不一致的降级路径（构造符号 simplify 超时/异常，必须返回 needs_human_check）
- Layer 2：homework-analysis 输出中 `verification_status` 枚举合法率 100%
- Layer 3：P4 验收报告须给出**实测**的 verification_status 分布，与本表目标对照并说明差距

实际执行结果见 commit 3 的测试输出（R25：未运行不声称通过）。
